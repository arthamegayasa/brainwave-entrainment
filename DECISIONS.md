# DECISIONS.md — ADR Log (append-only)

## ADR-001: Platform — Web App / PWA (2026-07-02)

**Context:** Pilihan antara PWA, mobile native (React Native/Expo), desktop (Electron/Tauri).
**Decision:** Web app / PWA.
**Rationale:** Web Audio API paling matang di browser; development & distribusi tercepat; installable di desktop & mobile. Trade-off yang diterima: background audio di iOS terbatas (mitigasi: Media Session API + screen-on guidance).
**Status:** Accepted (dipilih user via decision session).

## ADR-002: Scope MVP — Preset player dulu, builder menyusul (2026-07-02)

**Context:** EquiSync Element powerful tapi intimidating (frequency-first). Pilihan: preset player dulu vs full builder vs keduanya.
**Decision:** MVP = preset player berbasis tujuan (8 preset). Advanced builder ditunda ke M003.
**Rationale:** Cepat jadi & langsung berguna; menghindari UX intimidating; builder butuh fondasi engine yang sama sehingga tidak ada pekerjaan terbuang.
**Status:** Accepted (dipilih user).

## ADR-003: Target — Pemakaian pribadi, tanpa backend (2026-07-02)

**Decision:** Tanpa akun/pembayaran/backend. Preferensi & custom tweak disimpan di localStorage.
**Rationale:** Fokus ke kualitas audio & fungsi. Jalur upgrade ke produk publik tetap terbuka.
**Status:** Accepted (dipilih user).

## ADR-004: Audio 100% synthesized via Web Audio API (2026-07-02)

**Context:** EquiSync memakai file audio ter-render. Alternatif: file audio vs sintesis real-time.
**Decision:** Semua audio (entrainment tones, solfeggio, ambient noise) disintesis real-time dengan Web Audio API. Tanpa file audio.
**Rationale:** Frekuensi presisi (penting untuk binaural/solfeggio), durasi tak terbatas, ukuran app kecil, offline penuh, nol biaya hosting audio, dan memungkinkan ramp frekuensi kontinu (tidak mungkin dengan file statis).
**Consequences:** Kualitas ambient bergantung kualitas sintesis noise (filtered noise); perlu perhatian ke AudioContext autoplay policy (resume via user gesture) dan gain ramp untuk hindari click/pop.
**Status:** Accepted.

## ADR-005: Stack — Vite + React + TypeScript (2026-07-02)

**Decision:** Vite + React + TypeScript. State ringan (tanpa Redux). Styling: CSS modern (custom, calm dark theme, mobile-first).
**Rationale:** Iterasi cepat, TS penting untuk logika audio scheduler yang rawan bug angka, ekosistem PWA (vite-plugin-pwa) matang.
**Status:** Accepted.

## ADR-006: Session ramp sebagai inti "healing logic" (2026-07-02)

**Decision:** Setiap preset adalah kurva frekuensi (ramp turun dari ±kondisi sadar → target → hold → ramp naik di akhir; preset tidur tanpa ramp naik), bukan frekuensi statis.
**Rationale:** Meniru cara otak "dituntun" bertahap (frequency following response) — praktik standar program entrainment yang efektif, dan pembeda utama dari tone generator biasa.
**Status:** Accepted.

## ADR-008: Subscription pricing — IDR, Indonesia-first (2026-07-03)

## ADR-009: Payments — Midtrans-first via Supabase backend, multi-gateway (2026-07-03)

**Context:** User memilih Midtrans sebagai gateway (ideal untuk Indonesia: QRIS/VA/GoPay/ShopeePay/kartu + Subscription API). Midtrans IDR-only (regulasi Bank Indonesia), bukan Merchant-of-Record, dan — seperti gateway mana pun — wajib backend (Server Key rahasia + webhook verifikasi + entitlement server-verified).
**Decision:** Integrasi payment memakai backend **Supabase** (Auth + tabel `entitlements` + RLS + edge functions `create-transaction` Snap & `midtrans-webhook` verifikasi SHA512). Abstraksi `PaymentProvider` agar **Stripe/Merchant-of-Record** bisa ditambah untuk fase global tanpa mengubah frontend. Desain lengkap: `docs/payments/PAYMENTS-ARCHITECTURE.md`. Build ini hanya UI harga + scaffold; go-live menunggu Midtrans sandbox keys + project Supabase.
**Consequences:** **Men-supersede ADR-003 ("no backend")** khusus untuk permukaan monetisasi — backend diperkenalkan untuk payment + entitlement terverifikasi server. Audio engine & sintesis tetap 100% client-side. Recurring hands-off hanya untuk kartu; QRIS/VA/e-wallet perlu renewal via expiry + reminder.
**Status:** Accepted (design). Eksekusi backend = pass berikutnya saat kredensial tersedia.

## ADR-010: Behavioral-economics design layer (2026-07-07)

**Context:** Produk secara teknis lengkap tapi belum dirancang di sekitar pola pengambilan keputusan user. Prinsip behavioral economics (smart defaults, goal gradient, reciprocity, IKEA effect, loss aversion, contrast anchoring) terbukti menaikkan completion & conversion.
**Decision:** Enam prinsip diimplementasikan sebagai layer state client-side (`src/state/progress.ts`, localStorage `serenade.progress.v1`, pure TS tanpa React): (1) Smart default — kartu "Recommended now" berbasis jam lokal, one-tap start; (2) Goal gradient — journey 4 langkah yang step pertamanya auto-complete (tidak pernah 0%), streak dots Mon–Sun, session-complete view; (3) IKEA effect — goal picker skippable saat first visit, urutan grid dipersonalisasi; (4) Reciprocity — playback tidak pernah butuh akun; nudge upgrade hanya muncul setelah ≥2 sesi selesai dan dismissible; (5) Loss aversion — copy premium keep/protect-framing + blok personal stakes berbasis streak di Upgrade; (6) Contrast anchoring — anchor Rp588.000 (12× bulanan, dicoret) di samping hero tahunan Rp249.000.
**Consequences:** Semua state behavioral berada di localStorage (privacy-friendly, tanpa backend); angka harga tidak berubah — hanya framing. Konstanta `anchorAnnual` diturunkan dari harga bulanan di `tier.ts`.
**Status:** Accepted (implemented, quick task 260707-a47).

## ADR-011: Two-role system — Admin creates, User consumes (2026-07-07)

**Context:** Kebutuhan produk: Admin dapat membuat custom audio untuk Normal User; Normal User hanya memakai template goal-first bawaan + saved audio miliknya. Studio (advanced builder) terlalu kompleks untuk end user.
**Decision:** Role disimpan server-side di `public.profiles` (default 'user'; promosi admin hanya via SQL/service role — tidak ada jalur client). `public.is_admin()` (security definer, `set search_path = public`) dipakai policy RLS. Admin memakai Studio untuk mendesain lalu mem-publish ke `public.custom_audios` (spec JSONB) — sebagai template untuk semua user atau di-assign per user via `public.audio_assignments`. Normal User mendapat view **Library**: "Made for you" (cloud, sanitized on read via `sanitizeSession`) + "My saved sessions" (localStorage). Studio disembunyikan dari non-admin; fallback view ke Library. Override lokal `serenade.role.override` hanya dihormati saat Supabase tidak dikonfigurasi (demo/standalone mode).
**Consequences:** Semua spec audio dari cloud diperlakukan untrusted dan di-clamp sebelum menyentuh audio engine. Preset bawaan di-rename goal-first (Sleeping, Meditating, Relaxing, Calming Anxiety, Focus & Concentration, Boosting Energy, Creative Flow, Power Nap) dengan id tetap. Setup manual sekali: apply migration `0002_roles_library.sql` + promote admin pertama via SQL.
**Status:** Accepted (implemented, quick task 260707-a47).

## ADR-012: Clinician platform — multi-tenant, role-driven, 3-tier (2026-07-14)

**Context:** Produk berkembang dari "admin tunggal membuat audio" menjadi platform klinisi: banyak klinisi, masing-masing mengelola pasiennya sendiri (dashboard, kurasi template, Audio Bank, assign audio custom). Butuh isolasi antar-klinisi (multi-tenant) + monetisasi tier profesional.
**Decision:** Role diperluas jadi `user`/`clinician`/`admin` (`is_clinician()` security definer). Pasien terhubung ke SATU klinisi via invite code single-use (RPC `redeem_invite_code`, `FOR UPDATE` lock, 30 hari). Tiga tabel baru (`patient_links`, `invite_codes`, `template_visibility`) + kolom `category`/`notes` di `custom_audios`, semua RLS multi-tenant: klinisi hanya lihat/kelola pasien + audio miliknya sendiri; pasien hanya lihat miliknya. Publikasi template global tetap admin-only (RLS `with check is_template=false` untuk klinisi). Role di-drive oleh entitlement: webhook Midtrans mempromosikan `clinician` saat bayar plan clinician dan men-demote saat bayar premium atau order clinician gagal — dengan proteksi `provider_ref` agar order baru yang di-abandon tidak mencabut langganan aktif. Trigger `cleanup_patient_link` menghapus orphan curation/assignment saat link diputus. Pricing 3-tier IDR: Free Rp0, Premium Rp49rb/bln–249rb/thn, Clinician Rp249rb/bln–1,99jt/thn (anchor Rp2,988,000, hemat 33%, hingga 30 pasien, pasien mendengarkan gratis).
**Consequences:** Semua akses lintas-tenant dijaga RLS + `is_clinician()` gate (termasuk baca profil pasien). Role change hanya via webhook/service-role — tidak ada jalur eskalasi dari client. Deployed ke Supabase `pwvdobvbwoagvtzqyhfz` (migration 0005) + edge functions v2 + Vercel auto-deploy. **Keterbatasan (deferred):** demosi otomatis saat langganan clinician lapse tanpa order gagal butuh cron/expiry job — sama dengan keterbatasan renewal ADR-009.
**Status:** Accepted (implemented + deployed, quick task 260714-a8a).

## ADR-013: Satu AudioContext bersama dengan lifecycle perangkat (2026-09-25)

**Context:** Audio harus terdengar sama di perangkat berbeda. Audit menemukan: (1) dua `AudioContext` terpisah (preset + Studio) tanpa `latencyHint`; (2) iOS menaruh Web Audio di audio session `ambient` sehingga silent switch membisukan app; (3) interupsi OS (telepon, alarm, lock screen) membiarkan context `suspended`/`interrupted` tanpa umpan balik, dan `await ctx.resume()` yang tidak pernah selesai membuat tombol Start mati; (4) context idle terus me-render silence (baterai, memegang audio session); (5) noise ambience bergantung sample rate (level/warna berubah di 16k/96k/192k).
**Decision:** `src/ui/audioContext.ts` memiliki SATU context untuk SessionEngine dan BuilderEngine: `latencyHint: "playback"`, `navigator.audioSession.type = "playback"` (Safari 16.4+) sebelum dibuat dan di setiap play, `resume()` tanpa await (engine menjadwal di clock yang pause lalu berbunyi saat context jalan), auto-resume pada `statechange`/visibility/focus/gesture apa pun, banner "Resume audio" bila device menahan pause (atau start belum jalan setelah grace 1.5 s), dan suspend 1.5 s setelah tidak ada owner. Engine tetap context-agnostic (ENG-07). Noise disintesis per-Hz invariant terhadap sample rate (`NOISE_REFERENCE_RATE` 44.1 kHz). Engine membangun graph sebelum membaca `currentTime`.
**Consequences:** Start preset/custom kini sinkron (tidak ada lagi race "natural end mid-await"). Sesi yang di-interupsi pause di tempat karena mengikuti audio clock. Mode `playback` di iOS menghentikan musik app lain saat sesi dimulai (perilaku app musik/meditasi native). Carrier rendah di speaker kecil (174 Hz) tetap di luar kemampuan fisik speaker ponsel — keputusan produk terpisah.
**Status:** Accepted (implemented, quick task 260925-r7d).

## ADR-014: Akun Patient dimiliki Clinician — tanpa Invite Code, Link permanen, Admin mengawasi semua (2026-09-25)

**Context:** Clinician perlu mendaftarkan Patient yang belum tentu punya email atau kemampuan mendaftar sendiri, lalu memantau pemakaiannya terus-menerus. Alur ADR-012 (Patient mendaftar sendiri via magic link, menebus Invite Code, dan kedua pihak bisa memutus Link) tidak memenuhi itu.
**Decision:** Clinician dan Admin membuat akun Patient langsung (nama, email opsional, password; Premium langsung menyala). Email yang sudah punya akun ditolak untuk Clinician; hanya Admin yang bisa menautkan akun yang sudah ada, tanpa wajib memberi Username/password. Peran bisa rangkap: seorang Clinician boleh sekaligus menjadi Patient Clinician lain; Admin tidak bisa menjadi Patient. Invite Code dihapus: Link lama tetap dan menjadi permanen, kode yang belum terpakai dihapus, Premium Patient lama dinyalakan saat rilis, dan Clinician-nya boleh menambahkan Username + password. Patient tidak bisa memutus Link. Clinician-nya hanya bisa memutus Link (Patient jadi Regular yang tetap bisa login dengan Username + password, Premium pemberiannya mati, aksesnya ke Listening History hilang); menghapus akun dan Transfer ke Clinician lain hanya oleh Admin. Transfer mempertahankan Listening History, Premium, salinan password, dan Username; Assignment dan Hidden Preset dari Clinician lama dihapus. Admin bisa melakukan semua yang bisa dilakukan Clinician pemilik terhadap Patient mana pun dengan Audio Bank mana pun, membuat akun Clinician, serta menaikkan/menurunkan role Clinician; Clinician pemberian Admin kebal dari demosi karena pembayaran. Clinician yang kehilangan role karena pembayaran tetap terhubung dengan Patient-nya tetapi kehilangan akses; Admin melihat Patient itu bertanda "Clinician tidak aktif" dan bisa men-Transfer. Bila Admin sendiri yang menurunkan Clinician, Admin wajib men-Transfer Patient-nya lebih dulu. Batas Patient per Clinician default 30, bisa dinaikkan Admin per Clinician, dan dicek di server. Premium per Patient berlaku sampai dimatikan atau Link diputus (`ALL_UNLOCKED` tetap aktif, jadi belum membuka apa pun sampai gating dinyalakan). Berlaku untuk semua Clinician, bukan hanya Admin. Password hanya dimiliki Patient dan Clinician buatan Admin; Regular, Clinician berlangganan, dan Admin tetap login via magic link.
**Consequences:** Men-supersede jalur linking ADR-012 (`invite_codes`, `redeem_invite_code`, unlink dari sisi Patient). Pembuatan akun dan pengaturan password butuh jalur server (service role): client tidak bisa membuat user Auth maupun menulis `profiles` (0004). Admin butuh akses lintas-tenant ke `patient_links` dan `template_visibility`, yang sekarang hanya terbaca oleh pihak dalam Link itu sendiri (0005). Menolak email terdaftar bagi Clinician mencegah siapa pun yang membayar paket Clinician mengambil alih akun orang lain. Role Clinician butuh penanda asal (langganan vs pemberian Admin), karena webhook Midtrans sekarang menurunkan setiap `clinician` saat ia membeli Premium atau order clinician gagal.
**Status:** Accepted (design, grilling 2026-09-25). Password: ADR-015. Username & Personal URL: ADR-016. Listening History: ADR-017.

## ADR-015: Password Patient & Clinician buatan Admin bisa dilihat — salinan terenkripsi + catatan akses (2026-09-25)

**Context:** Clinician ingin selalu bisa memberi tahu Patient password-nya, termasuk password yang diganti Patient sendiri; Admin menginginkan hal yang sama untuk Clinician yang ia buat. Supabase Auth hanya menyimpan hash satu arah; tidak ada yang bisa membacanya kembali.
**Decision:** Selain hash di Auth, simpan salinan password yang terenkripsi dan hanya didekripsi di server: password Patient untuk Clinician pemiliknya dan Admin; password Clinician buatan Admin untuk Admin. Password Patient yang juga Clinician hanya bisa dilihat dan di-reset Admin, supaya satu Clinician tidak bisa masuk sebagai Clinician lain (dan data Patient-nya). Salinan dihapus saat Link diputus. Setiap kali password ditampilkan, tercatat siapa, kapan, dan milik siapa; Admin bisa membaca catatan itu. Satu baris kecil di bawah kolom password baru menyebut bahwa password itu bisa dilihat (tanpa popup), dan kebijakan privasi menjelaskannya.
**Considered Options:** Password hanya terlihat sekali saat dibuat atau di-reset, lalu tinggal hash (direkomendasikan untuk Patient dan Clinician, ditolak user): Clinician/Admin tidak bisa melihat password yang diganti pemilik akun sendiri.
**Consequences:** Kebocoran database beserta kuncinya, bug akses, atau satu Clinician berniat buruk membuka password apa adanya, termasuk password Clinician yang bisa membuka data puluhan Patient; karena orang memakai ulang password, dampaknya keluar dari Serenade (email, bank). Kunci enkripsi wajib disimpan di luar database. Catatan akses menjadi satu-satunya cara mendeteksi penyalahgunaan. Menambah beban kepatuhan UU PDP di atas Listening History.
**Status:** Accepted (keputusan user, grilling 2026-09-25).

## ADR-016: Username + Personal URL `/p/<username>` (2026-09-25)

**Context:** Patient belum tentu punya email, tapi harus bisa masuk cukup dengan password lewat alamat yang dikirim Clinician-nya.
**Decision:** Setiap Patient punya Username unik se-platform. Personal URL = `serenade.com/p/<username>`: menampilkan nama depan Patient dan satu kolom password; di perangkat yang sudah login langsung masuk. Login di homepage menerima email atau Username + password. Bila Username diganti, Personal URL lama terus mengalihkan ke yang baru sampai Username lama diambil Patient lain, dan Username lama dikunci 30 hari sebelum boleh diambil; Username akun yang dihapus juga dikunci 30 hari. Username dan login password tetap berlaku setelah Link diputus.
**Considered Options:** `serenade.com/<username>` (bentrok dengan halaman app sekarang dan yang akan datang); `serenade.com/<clinician>/<username>` (Username boleh sama antar-Clinician, tapi URL berubah saat Transfer); `serenade.com/p/<username>-<kode acak>` (tidak bisa ditebak, tapi sulit diingat dan diketik).
**Consequences:** Username bisa ditebak, sehingga keberadaan seorang Patient dan nama depannya terbuka bagi siapa pun yang mencoba URL; perlindungan sepenuhnya ada di password dan pembatasan percobaan login. App sekarang tidak punya URL routing (`App.tsx` memakai state `view`), jadi butuh router dan rewrite SPA di hosting.
**Status:** Accepted (design, grilling 2026-09-25).

## ADR-017: Listening History tersimpan di server untuk semua User yang login (2026-09-25)

**Context:** Clinician perlu memantau pemakaian Patient: audio apa, berapa kali diulang, dan jam berapa. ADR-010 sengaja menyimpan data perilaku hanya di perangkat.
**Decision:** Setiap Play dari User yang login (bukan hanya Patient) dikirim ke server; Play saat offline dikirim begitu online. Putaran di bawah 30 detik dan putaran uji di Studio bukan Play. Unduhan MP3 tercatat sebagai Download, terpisah dari Play, karena pemutaran di luar app tidak bisa dilacak. Jam ditampilkan dalam zona waktu Patient. Listening History disimpan selama akunnya ada, dan terlihat oleh User itu sendiri (di Account), Clinician-nya bila ia Patient, dan Admin. Pemantauan hanya dijelaskan di kebijakan privasi: tanpa layar pemberitahuan dan tanpa opsi menolak, demi alur yang mulus. User yang belum login tetap hanya tercatat di perangkat.
**Consequences:** Men-supersede sifat "lokal saja" ADR-010 untuk User yang login. Riwayat dengar yang dipantau Clinician kemungkinan besar termasuk data kesehatan (data spesifik, UU PDP Pasal 4 ayat 2), dan pemrosesan berbasis persetujuan wajib menyampaikan tujuan, jenis data, retensi, dan hak subjek (Pasal 21 ayat 1); app belum punya kebijakan privasi, jadi halaman itu ikut dibangun (draf bahasa Indonesia + Inggris, ditinjau user atau penasihat hukum sebelum rilis). Pencatatan harus mencakup dua jalur pemutaran: Preset (SessionEngine) dan Custom Audio (BuilderEngine).
**Status:** Accepted (design, grilling 2026-09-25).

## ADR-018: Login Username lewat email login internal + endpoint resolve login (2026-09-26)

**Context:** Sign-in password Supabase Auth butuh alamat email, sedangkan Patient buatan Clinician belum tentu punya email dan harus bisa masuk dengan Username + password (ADR-016). Email asli Patient, bila ada, tidak boleh terbuka bagi siapa pun yang menebak Username-nya, dan pembatasan percobaan sign-in per IP dari Supabase Auth harus tetap berlaku.
**Decision:** Setiap akun yang dibuat Clinician atau Admin dengan Username login memakai email login internal `<uuid acak>@login.serenade.invalid` (TLD `.invalid` dicadangkan RFC 2606 dan tidak pernah menerima email) yang tidak pernah ditampilkan ke siapa pun. Email asli, bila ada, disimpan sebagai contact email (`profiles.contact_email`). Endpoint publik `resolve-login` memetakan Username atau contact email ke "password, dengan email login ini", dan email lain ke "magic link"; Username yang tidak dikenal dijawab "tidak ditemukan". Client lalu memanggil sign-in password Supabase biasa dengan email login itu. Form sign-in menerima email atau Username: akun password mendapat kolom password, akun lain tetap mendapat magic link. Clinician buatan Admin tetap memakai email aslinya sebagai email login. "Email sudah terdaftar" berarti cocok dengan email login atau contact email akun mana pun.
**Considered Options:** (1) Resolve Username ke email asli lalu sign-in dengan email itu: siapa pun yang menebak Username mengetahui email Patient. (2) Sign-in di dalam edge function (Username + password dikirim ke server, server yang sign-in): semua percobaan datang dari IP server yang sama, sehingga rate limit per IP Supabase Auth tidak lagi membatasi penebak password.
**Consequences:** Email login internal dibuat acak, bukan dari Username, sehingga mengganti Username tidak menyentuh Auth. App tidak pernah menampilkan email login mentah: yang tampil adalah contact email, atau email login bila bukan internal (`shownEmail` di modul Account rules, `supabase/functions/_shared/accountRules.ts`, modul yang juga dipakai server functions untuk izin dan aturan Username). `resolve-login` membuka satu fakta, yaitu apakah suatu Username atau email milik akun password; ini risiko yang sama dengan Personal URL (ADR-016), dilindungi password dan rate limit Auth, dan jawabannya tidak pernah berisi email asli. Form tidak lagi mengirim magic link ke contact email Patient (yang akan membuat akun baru yang kosong), tetapi `signInWithOtp` yang dipanggil langsung lewat API masih bisa membuat akun terpisah dengan email itu. Pembuatan Patient berjalan di edge function `create-patient` (service role) yang memutuskan izin lewat modul Account rules, sedangkan batas Patient dicek ulang di database di bawah lock (`link_new_patient`). Supabase hosted harus menerima domain `.invalid` pada admin `createUser`; ini baru terverifikasi di stack lokal.
**Status:** Accepted (implemented, #5).

## ADR-019: Clinician buatan Admin — asal role, login password lewat salinan password, batas Patient (2026-09-26)

**Context:** ADR-014 menetapkan bahwa role Clinician mencatat asalnya (langganan atau pemberian Admin) dan bahwa webhook pembayaran hanya menyentuh Clinician langganan. Saat Admin mulai membuat dan mempromosikan Clinician (#14), empat hal belum diputuskan: bagaimana Clinician buatan Admin login dari homepage (`resolve-login` menjawab "magic link" untuk setiap email asli), bagaimana User yang dipromosikan login, sejauh mana Admin boleh mengubah batas Patient, dan apa yang terjadi pada asal role saat webhook menurunkan seseorang.
**Decision:** (1) Sebuah email mendapat langkah password bila akunnya menyimpan salinan password (`password_login_email`, 0014). Setiap Clinician buatan Admin punya salinan sejak dibuat, jadi langsung login dengan email + password; User yang dipromosikan Admin, termasuk arthamegayasa@gmail.com, tetap memakai magic link sampai Admin me-reset password-nya sekali. (2) Admin mengisi batas Patient berupa bilangan bulat dari jumlah Patient Clinician itu saat ini sampai 1000: salah ketik bisa dibetulkan, tapi batas tidak pernah di bawah Patient yang sudah ada. (3) Form "+ Create clinician" meminta nama (wajib), email, dan password (ketik atau Generate); email yang sudah terdaftar ditolak dan Admin mempromosikan User itu. (4) "Make clinician" tersedia untuk setiap User tanpa role Clinician (Regular, Patient, Inactive Clinician), tidak pernah untuk Admin. Webhook yang menurunkan Clinician langganan juga menghapus asal role-nya (tanpa role, tanpa asal). Saat rilis, Clinician dengan langganan clinician berstatus `active` menjadi "subscription", sisanya "admin".
**Considered Options:** Semua Clinician pemberian Admin langsung mendapat langkah password (ditolak: User yang dipromosikan tanpa password terkunci dari magic link sampai Admin me-reset). Batas Patient hanya boleh naik (ditolak: salah ketik tidak bisa dibetulkan). Form tanpa nama (ditolak: tab Admin menampilkan nama).
**Consequences:** Keputusan role setelah pembayaran ada di modul Account rules (`clinicianRoleAfterPayment`) dan diuji Vitest; webhook hanya menulis hasilnya, dan hanya bila role yang dibacanya belum berubah. Promosi, batas Patient, dan pembuatan Clinician berjalan di edge function `promote-clinician`, `set-patient-limit`, dan `create-clinician` yang memutuskan izin lewat Account rules; `complete_new_clinician()` (0014) memberi role dan menyimpan salinan password dalam satu transaksi. Clinician dengan langganan `pending` saat rilis ikut menjadi "admin".
**Status:** Accepted (keputusan owner lewat koordinator, implemented #14).

## ADR-020: Transfer Patient dan pencabutan role Clinician (2026-09-26)

**Context:** ADR-014 menetapkan bahwa hanya Admin yang men-Transfer Patient (Listening History, Premium, salinan password, dan Username ikut; Assignment dan Hidden Preset Clinician lama dihapus) dan bahwa Admin wajib men-Transfer Patient seorang Clinician sebelum mencabut role-nya. Saat membangun #15, empat hal belum diputuskan: siapa yang boleh menjadi tujuan Transfer, apa yang terjadi bila batas Patient tujuan tidak cukup untuk semua Patient yang dipindahkan, apakah waktu Link berubah, dan apa yang terjadi pada salinan password Clinician buatan Admin yang role-nya dicabut.
**Decision:** (1) Tujuan Transfer adalah pemegang role Clinician atau Admin (Admin tanpa batas Patient); bukan Clinician Patient itu sekarang, bukan salah satu Patient yang dipindahkan, dan bukan Inactive Clinician. (2) Transfer berlaku untuk semua Patient yang dipilih atau tidak sama sekali: ditolak bila batas Patient tujuan tidak cukup untuk semuanya, lalu Admin menaikkan batas atau memilih tujuan lain. (3) Transfer memindahkan baris Link (`patient_links.clinician_id`); `created_at` dan Premium grant Link tetap. Trigger `on_patient_link_moved` (0015) menghapus Assignment audio dari Audio Bank Clinician lama dan Hidden Preset atas nama Clinician lama, seperti saat Link diputus, tetapi salinan password tetap. (4) Mencabut role Clinician membuat role `user` tanpa asal, dalam satu transaksi setelah Transfer, dan ditolak selama masih ada Patient. Orang itu menjadi Regular, atau tetap Patient Clinician-nya. Salinan password-nya dihapus kecuali ia Patient (Regular tidak menyimpan salinan, `keepsPasswordCopy`), sehingga Clinician buatan Admin kembali login lewat magic link.
**Considered Options:** Transfer sebagian sampai batas penuh (ditolak: sisa Patient tertinggal tanpa kejelasan). Salinan password Clinician buatan Admin tetap disimpan setelah role dicabut (ditolak: tidak ada yang boleh membacanya). Hanya pemegang role Clinician sebagai tujuan (ditolak: Admin sudah memegang semua kuasa Clinician dan punya Patient sendiri).
**Consequences:** Izin diputuskan di Account rules (`mayTransferPatients`, `mayRemoveClinicianRole`) dan diuji Vitest; edge function `transfer-patients` dan `remove-clinician-role` memakai modul itu, lalu `transfer_patients()` dan `remove_clinician_role()` (0015, hanya service role) memeriksa ulang di bawah kunci baris profil kedua pihak, dengan urutan tetap agar dua Transfer tidak saling deadlock. `link_new_patient()` mengunci profil yang sama, jadi pembuatan Patient dan Transfer ke Clinician yang sama bergiliran dan batas dihitung dari Link yang benar-benar ada. Penolakan untuk tujuan tanpa role (`target_not_clinician`) terpisah dari `not_clinician` (akun yang role-nya hendak dicabut).
**Status:** Accepted (keputusan owner lewat koordinator, implemented #15).

## ADR-021: Admin menautkan User yang sudah ada sebagai Patient; Username + password untuk Patient tanpa Username (2026-09-26)

**Context:** ADR-014 menetapkan bahwa hanya Admin yang menautkan akun yang sudah ada sebagai Patient, tanpa wajib memberi Username/password, dan bahwa Clinician boleh menambahkan Username + password untuk Patient lama; spec #3 (story 18) meminta Clinician atau Admin bisa menambahkannya belakangan. ADR-018 menetapkan bahwa akun dengan Username login memakai email login internal dengan email asli sebagai contact email. Saat membangun #16, empat hal belum diputuskan: dari mana Admin menautkan, siapa yang boleh menambahkan Username + password belakangan, apa yang terjadi pada bekas Patient yang masih punya Username, dan urutan database dan Auth saat akun yang sudah ada dipindah ke email login internal.
**Decision:** (1) Admin menautkan dari tiga tempat: "Link to clinician…" di drawer setiap User yang bukan Patient (Regular, Clinician, Inactive Clinician), "+ Link existing user…" di daftar Patient seorang Clinician (tampilan "Patients of …"), dan "Link as my patient" di bawah penolakan "email already registered" pada "+ New patient" milik Admin sendiri. Clinician tetap hanya mendapat penolakan itu. Clinician tujuan harus memegang role Clinician atau Admin (bukan Inactive Clinician, bukan akun itu sendiri) dan masih punya tempat di bawah batas Patient-nya, seperti Transfer; akun Admin ditolak (`account_is_admin`), di Account rules dan lagi di database di bawah kunci. Link baru membawa Premium grant. (2) Username + password opsional saat menautkan (keduanya atau tidak sama sekali), dan bisa ditambahkan belakangan untuk Patient tanpa Username oleh orang yang boleh me-reset password-nya: Clinician-nya sendiri, kecuali Patient itu juga Clinician, dan Admin. "Juga Clinician" mencakup Inactive Clinician yang masih punya Patient: role-nya bisa kembali, jadi password-nya, untuk dibuka, di-reset, atau ditambahkan, hanya urusan Admin (keputusan owner lewat koordinator; berlaku juga untuk reveal dan reset dari #8). Hanya Patient yang mendapatkannya; akun yang sudah punya Username (mis. bekas Patient yang ditautkan lagi) tetap memakai Username dan password-nya sendiri, dan Username diganti lewat "Change username". (3) Email login akun saat itu menjadi contact email (huruf kecil), akun mendapat email login internal acak baru dan salinan password (menggantikan salinan Clinician buatan Admin); Auth mengakhiri sesi lamanya, dan homepage sejak itu meminta password untuk email tersebut. (4) Database lebih dulu (`add_username_login()`, di bawah kunci profil), baru Auth (`updateUserById` dengan email, password, `email_confirm`); bila Auth menolak, profil, salinan password, dan Link yang dibuat request itu dikembalikan. Selama di antara keduanya contact email akun masih sama dengan email loginnya, dan `password_login_email()` (0016) tidak menjawab Username atau contact email akun dalam keadaan itu, sehingga Username tidak pernah dijawab dengan email asli.
**Considered Options:** Auth lebih dulu (ditolak: bila langkah database gagal, akun tertinggal dengan password yang diketahui Admin, mungkin tanpa Link, dan password Clinician buatan Admin tidak lagi sama dengan salinannya). Menambah Username + password belakangan hanya oleh Admin (ditolak owner: ADR-014 memberi Clinician hak itu untuk Patient-nya). Tanpa entri di "+ New patient" (ditolak owner: spec menyebut Admin boleh menautkan akun itu sebagai gantinya).
**Consequences:** Keputusan ada di Account rules (`mayLinkExistingAccount`, `mayAddUsernameLogin`, `usernameLogin`, `checkUsernameLogin`, `checkLinkLogin`) dan diuji Vitest; edge function `link-patient` dan `add-username-login` (keduanya membaca `PASSWORD_COPY_KEY`) memakai modul itu, lalu `link_existing_patient()` dan `add_username_login()` (0016, hanya service role) memeriksa ulang di bawah kunci; `link_existing_patient()` mengunci profil kedua pihak dengan urutan yang sama seperti `transfer_patients()`. Listening History dari sebelum Link langsung terlihat oleh Clinician barunya (ADR-017). Di Dashboard Clinician, password Patient yang juga Clinician tidak bisa dibuka atau di-reset: drawer menyebut bahwa hanya Admin yang bisa. Clinician hanya membaca Link miliknya sendiri, jadi drawer-nya tidak tahu bahwa seorang Patient adalah Inactive Clinician: tombolnya tetap tampil dan server menolak dengan "hanya Admin"; server membaca jumlah Patient akun itu (`PasswordAccount.patientCount`). Admin menemukan akun di balik email terdaftar lewat `user_overview()` miliknya, tanpa fungsi server baru.
**Status:** Accepted (keputusan owner lewat koordinator untuk titik masuk, siapa yang menambah Username + password, dan Inactive Clinician; implemented #16).
